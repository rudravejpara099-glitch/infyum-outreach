# At-cost billing: TEST implementation

Branch `feat/billing-at-cost`, PR #7 (integrated on `feat/platform-integration`, PR #12). No subscription, automatic debit or live-mode path. The official Stripe SDK is the only added dependency; it supplies hosted checkout and raw-body signature verification. No new service, queue or ORM. Migration 2 adds billing tables without changing shipped migration 1 or assigning historical work.

## What users see

Usage and billing shows recorded costs, today’s total, a projection based on recorded variable spend and confirmed future expenses, held/committed amounts, a monthly ceiling, statements and CSV downloads. Empty usage remains zero. Users pay recorded costs and the processor’s actual fee only; there is no margin or subscription tier. Statements show usage, prior carry, fee corrections and the estimated processor fee separately. Finalized amounts do not change. Account/campaign payer assignment is explicit and requires reviewed integration; existing active campaigns/pending work cannot be claimed silently. Owner controls return 404 to other users; statement access belongs to its payer or the designated owner. CSV export is scoped and spreadsheet-formula safe.

Amounts are integer USD micro-dollars. Whole-cent checkout rounding creates a disclosed credit carried forward. Amounts below the processor minimum carry forward without an overdue penalty. Actual processor fees replace the estimated fee through an adjustment on the next statement, never by rewriting a paid statement or increasing its checkout. A credit-only statement charges no fee. Calendar months and statement dates use UTC; overdue starts seven days after issuance. Usage views/downloads remain available during a hold.

Paid work starts off (ceiling zero). Atomic immediate SQLite reservations count actual usage, pending positive fee adjustments, confirmed future fixed expenses, fees and holds across all lanes before the 90% cutoff. Unresolved operations retain their holds across restarts/months. Reusing an unresolved operation returns `fresh: false`, which must never dispatch another paid call. Charged failures are recorded; provider overruns are recorded honestly and pause further work for review. See BILLING-INTEGRATION.md for the mandatory worker contract and authoritative Apify aggregate requirements.

## Owner setup, privately

Set an explicit existing `BILLING_OWNER_USER_ID`; no first-user or email-based authority is inferred. Set `APP_URL` to the app’s trusted origin. Configure `STRIPE_SECRET_KEY` with an `sk_test_` key and the matching `STRIPE_WEBHOOK_SECRET` in ignored local configuration. Live keys and live events are refused. Do not put credentials in chat, docs, shell output or the board. `BILLING_DEPLOYMENT` defaults to local; hosting is always zero locally. Creating an app server against an existing real database applies migration 2, so back it up and coordinate first; this task has not started that server.

Configure Stripe TEST webhook delivery to `/api/billing/webhook` for checkout.session.completed, checkout.session.async_payment_succeeded, checkout.session.async_payment_failed, checkout.session.expired, charge.succeeded and charge.updated. This exact route is public because it authenticates the unmodified body using the provider signature/timestamp; other routes retain normal login checks. No redirect or unsigned request can mark a statement paid. One active checkout attempt per statement and durable idempotency keys prevent duplicate retries; unresolved creation older than 20 hours stops for reconciliation rather than risk an expired idempotency key. Fees still missing their balance transaction stay pending. The owner can retry fee reconciliation from administration.

Only confirm real vendor expenses, with their evidence reference. Network costs allocate the confirmed monthly amount by UTC calendar day, exactly across a full month; partial months accrue only assigned days. Hosting uses a confirmed daily allocation when hosted. Initial expenses begin today; changes begin tomorrow. Future confirmed expense amounts count against the ceiling; stopping an expense uses a new zero version. Do not add passwords, full card details or sensitive invoice contents as references. Processor fee changes take effect next UTC month, with immutable history. The legacy migration column for margin is retained for schema compatibility, but reads, writes and statement calculations force it to zero. Exact AI models need verified input/output/cache prices; missing cache prices or the unverified placeholder refuse dispatch.

The seed model is explicitly labelled “update from the provider’s price page”: $3 input and $15 output per million tokens. The supplied 100,000 input and 22,000 output tokens calculate to $0.63/day at those placeholder rates; the rough $1–$2 planning range is not a charge. Network $10/month/account, hosted $0.60/day and Apify $1.05/day are planning figures only; no seed turns into user usage. Local hosting stays $0. Neither rough daily total is shown as actual spend.

## Verification and limitations

`npm test` covers exact arithmetic with no margin, fee gross-up, credits/minimum amounts, UTC boundaries, model snapshots, consent/assignment timing, immutable history, atomic settlement/replays, unknown outcomes, Apify cap enforcement, grace/holds, owner authorization, checkout/webhook validation and separate-process concurrency. `npm run smoke:billing` creates a disposable database, loopback-only provider simulator and local app; it checks actual pages/actions/SDK redirects, declined then successful simulated payment, duplicate signed deliveries, fee correction, scoped CSV and other-user rejection. It takes screenshots of all billing pages at 1440/1024/390px in light and dark. `npm run smoke:ui` remains separate and disposable. Neither starts the worker or uses the owner’s database.

The simulator is NOT an actual Stripe TEST-account checkout. Actual provider verification requires privately configured TEST credentials and an accessible signed webhook endpoint. No such credentials were present during implementation. `BILLING_TEST_API_BASE` is only for the loopback simulator and is refused in production; do not configure it for a provider-account test. A production build can validate compiled code without enabling any provider.
